## 1. FINDING — `config.yaml` is baked into the image, so a restart cannot apply it

**Discovered by reading, prompted by the owner refusing to accept an inference from my
own exploration note. Nothing on the server was touched or tested to establish it.**

Every path by which the running container could obtain a config:

| Path | Evidence | Result |
|---|---|---|
| Bind mount for `app` | `docker-compose.yml` — the `app` service's keys are `build, restart, logging, env_file, environment, depends_on, ports, healthcheck` | **no `volumes:` key.** (`postgres` has one, for `pgdata`; there is also a top-level `volumes:` declaration. Neither mounts a config.) |
| Image copy | `Dockerfile:16` `COPY config.yaml ./`, `Dockerfile:8` `WORKDIR /app` | the file lands at `/app/config.yaml`, **in an image layer** |
| Path resolution | `sentinel/core/config.py:1079` `Path(os.getenv("CONFIG_PATH", str(DEFAULT_CONFIG_PATH)))`, `:30` `DEFAULT_CONFIG_PATH = Path("config.yaml")` | relative to CWD, i.e. `/app` |
| Env override | `.env.example:16` `CONFIG_PATH=config.yaml`, delivered by `env_file: .env` | relative; with no mount it can only resolve **inside** the image |
| Dev overlay | `docker-compose.dev.yml` | publishes a Postgres port. No `app` service, no volumes. |
| Any other override | `ls` | only those two compose files exist |

**So `docker compose restart app` restarts the existing container from the existing
image, and a host-side edit of `/opt/sentinel/config.yaml` reaches nothing — silently,
exit 0.** Plain `docker compose up -d` is also a no-op: Compose recreates a container
only when its *definition* changes, and editing a host file does not change it.

**The correct procedure is `docker compose up -d --build app`.** Proven twice over: the
repo's own local analogue `make restart` is `$(COMPOSE) up -d --build app`
(`Makefile:117`), and `ops/update.sh` runs `compose build app` then `compose up -d`,
which is the only documented path that has ever actually applied a config change.

### What this broke

**`docs/DEPLOY.md` §13 step 3 — the going-live command — was wrong twice over and could
never have worked.**

```bash
sed -i 's/^dry_run: true/dry_run: false/' config.yaml    # anchored to ^; dry_run is indented
docker compose restart app                               # cannot apply a config change
```

The `sed` is anchored to line start. Since M10a the only `dry_run` keys are
`markets.crypto.dry_run` and `markets.forex.dry_run`, both indented four spaces. It
matched nothing, changed nothing, and **exited 0**. Had the `sed` worked, the `restart`
would have discarded it anyway. Run as written, the operator would see no output, no
error, and a system still in rehearsal — while believing it had gone live.

§6's `grep -n "^dry_run" config.yaml` carried the identical anchor defect and returned
nothing at all, which reads exactly like "the file is fine". **The owner's brief named
the `sed`; §6 was found in passing and is the same bug.** §13b step 5 had the `restart`
half.

**Inference, labelled as such because the server cannot be read from here:** going live
on 2026-08-19 happened another way — by committing `dry_run: false` (`config.yaml:24-30`
dates that to an owner instruction) and deploying through §12, which rebuilds. **The
documented procedure survived because nobody ever ran it.** That is the whole mechanism
by which this class of defect persists: a runbook step is only tested on the day it is
needed, which is the worst possible day to find out.

### The second consequence, which raised the value of item 2

`Dockerfile:16` (`COPY config.yaml`) sits **above** `:18` (`RUN pip install .`). Busting
the config layer therefore forces a full dependency re-resolution. **Every server-side
config change re-rolls every unpinned dependency** — so a correctly executed §13 go-live
would itself have silently moved `ccxt`, `pandas` and `uvicorn` underneath the live
system, as a side effect of turning off dry run.

### Fixed

§6, §13 and §13b step 5 now use `docker compose up -d --build app`, and every one of them
ends by reading the value back off `scheduler.pipeline_scheduled` **from the running
container**, with the doc saying in as many words that the file on disk is not evidence
about what is running. §8.2 now shows the full expected line.

## 3. LESSON — a check that compares two things to each other cannot see them moving together

**This is `pandas`' lesson, and it is not `numpy`'s.** They look alike and they are
opposites.

- **numpy was VISIBLE to `check_pins`.** The two sides disagreed — 2.2.6 against 2.5.2 —
  and the tool warned. A dev extra was holding one side back, the check compared the two,
  and the difference showed.
- **pandas was INVISIBLE to it.** `.venv` and the image both resolved 3.0.5, so there was
  nothing to report. But the declaration said `>=2.2`, and both environments had drifted
  across a **major version boundary** into pandas 3.x by ordinary resolution, with nothing
  anywhere recording that it had happened.

**"Floating together" and "pinned" are indistinguishable to a check that only compares two
sides to each other.** `check_pins` reported silence, and silence was correct — it just
was not the question anybody thought it was answering.

This is a shape this repository has now hit three times:

1. the golden that pinned **one price magnitude**, and so could not see a bug that only
   appears at another;
2. `test_no_arithmetic` comparing `Decimal`s **as strings**, because `==` is precisely the
   comparison that could not see the capital defect — `Decimal("10.0") == Decimal("10")`;
3. **this** — two environments compared against each other, with no third point of
   reference.

Each reads as thorough while being structurally unable to see the thing it is aimed at.

**What actually catches this class: compare against something OUTSIDE the two
environments.** A declared exact version, a lockfile, a recorded version stamped from a
run that produced evidence. Not the two sides against each other — that only ever finds
*divergence*, and divergence is a strictly weaker property than *correctness*. The `==`
pin is the cheapest form of the outside reference, which is why the answer here was to
pin rather than to widen the floor to `>=3.0`.

**The mitigating fact, so the record is not more alarming than the situation.** All 37
goldens are byte-identical across the pin. pandas 3.0.5 is what `.venv` already had, so
**pandas 3.x produced every number in the open measurement window**, and the pin freezes
exactly that. There is nothing to unwind and nothing to re-measure. What was wrong was the
bookkeeping, not the numbers.

`HANDOFF.md` §4 item 14 carries a dated correction: its closing sentence assumed this
stack sat near the `>=2.2` floor, and the resolution had left that floor behind long ago.

## 4. LESSON — the golden suite proves the renderer did not change, not that the card did not

**A process lesson, and an owner-side one. Recorded as a process failure, not a code
defect, so the next deploy does not repeat it.**

M10c §14 promised that the only user-visible change of the deploy would be `€200.00` and
`0.75%` where eighteen decimal places used to print, and that **nothing else on either
card may differ**. On the day, the `/status` BEFORE-picture was **not captured** before the
restart. The owner's instruction was to capture it; it was not followed through.

So "no third line moved" rests on the owner reading the new card against **memory**. That
is weaker than intended, and the M10c report now says so instead of implying a check that
was not performed.

The tempting defence is that `tests/golden` pins every surface byte for byte and none of
them moved. That defence does not hold, and the distinction is the lesson:

> **The golden suite proves the RENDERER did not change. It cannot prove the live card
> matches yesterday's, because it never saw yesterday's.** Those are two different claims
> and only the first was tested.

A golden compares today's renderer against a committed fixture. It says nothing about the
*data* the live system rendered, about DB overrides, or about anything that reached the
card by a path the fixture does not model.

**The rule, for next time:** when a deploy changes a rendered surface, capture the live
surface **as text** before the restart, and diff it after. Once the container is recreated
the before-picture is gone for good and the check downgrades to memory. It costs one
copy-paste and it is the only thing that makes "nothing else moved" a verified statement.

The same day produced a second, smaller instance: **M10c §11's bare `tracker` job id could
not be confirmed from the server at all**, because APScheduler logs the function name —
`_schedule_pipeline.<locals>.track_for.<locals>.track`. What was verified is that the track
job has executed successfully every 60 seconds since boot, which shows *a* tracker is
running, not which id it holds. Item 6 below closes that.

## 5. CONVENTION — dated notes for specs, corrected text for runbooks

**Settled with the owner this session, and it is a project convention rather than a
decision about one section.**

`docs/specs/ENSEMBLE.md`'s 2026-08-20 block set the house style: a dated correction above
text left deliberately unedited, because *a spec that quietly rewrites itself cannot be
checked against the decision it recorded.* That reasoning is exactly right — for a spec.

**It does not transfer to a runbook.** `docs/DEPLOY.md` §13 step 3 is not a record of a
decision; it is a command somebody pastes into a live server at the moment they turn real
money on. Leaving a broken version standing beneath a correction preserves the record and
leaves a landmine, and the two are not worth trading against each other.

The convention, therefore:

- **Specs and journals** — dated note **above**, original text **untouched**. The record is
  the point. (This is why `journal/M10a_REPORT.md` and `journal/M10b_2_REPORT.md` were left
  alone this session even though both repeat the stale claim: they are dated records of
  what was believed then.)
- **Runbooks** — **correct the executable text in place**, and quote the old command *inside*
  the correction block with an explanation of why it was wrong. The record survives in the
  block; the landmine does not survive in the runbook.
- **Forward-looking operational instruction inside a journal** takes the runbook rule.
  `journal/M10c_REPORT.md` §14 is instruction for a future switch-on day, not a finding, so
  it was corrected rather than merely annotated.

## 7. The standing hazard — live mode is now a committed value

Documented in `docs/DEPLOY.md` §12 and §13. Because the server's `config.yaml` has no local
edits, `dry_run: false` lives **in git**. The old safeguard was accidental: `git pull
--ff-only` **refusing** to run against a locally-modified config forced somebody to read the
diff. **That safeguard is gone precisely because the file is clean.**

A flip merged from a laptop now deploys silently — `ops/update.sh` pulls, rebuilds, restarts,
reports healthy, and `Dockerfile`'s `COPY config.yaml ./` bakes it in with nothing mounted
over it. Nobody is asked anything.

Two mitigations, with their limits stated rather than implied:

1. **`ops/update.sh` prints `git diff <previous> HEAD -- config.yaml`** after the pull and
   before the build. It says `config.yaml: unchanged in this update` when there is nothing,
   so **silence is never ambiguous** — which is the exact failure mode of the two §13 defects.
   This is the only mitigation that reaches the server.
2. **`make check` fails on a flip**, by name. **This gates the commit, and only if somebody
   runs the gate. There is no CI in this repository.** It does not protect the server.

**To go quiet in a hurry, `/pause`** — a Telegram command, no deploy, no rebuild, and the
tracker keeps managing anything already open. Not a config edit, which per §1 would not even
take effect without a rebuild.

### On the guard itself — a smaller claim than the brief assumed

Both flips **already failed the suite** before this session, by accident:

- `markets.forex.enabled` — through `test_the_shipped_config_is_still_single_market` and
  `test_forex_ships_disabled_and_unimplemented`, both of which assert it directly;
- `markets.crypto.dry_run` — through `test_the_new_config_and_the_legacy_one_agree_about_crypto`,
  *indirectly*, because it `model_dump`-compares crypto against a frozen fixture that happens
  to pin `false`.

**So the new test is a diagnostic, not a new safety net.** What it buys is a failure that says
what happened. The contrast, for the identical `dry_run` flip:

```
# the accidental guard:
E  AssertionError: assert {'enabled': T...} == {'enabled': T...}
E    Differing items:  {'dry_run': True} != {'dry_run': False}

# the new one:
E  AssertionError: markets.crypto.dry_run is committed as False — the crypto measurement
   window is live. If you meant to enter dry run, that is a deliberate change to what
   ships and this test changes with it. If you are in an incident, use /pause.
```

Proven by flipping each value in the working tree in turn and capturing the failure, then
restoring: `git diff main -- config.yaml` **empty**.

**Answering the owner's two objections rather than agreeing with them:**

- *Entering dry run deliberately would require editing a test.* Weak — but **not for the reason
  I first gave**. My draft claimed a server-side `config.yaml` edit was the incident lever and
  restored the `--ff-only` safeguard. §1 killed that: the edit changes nothing until a rebuild.
  The real lever is `/pause`. (One clause survives: a server-side edit does still make the file
  dirty and break `--ff-only` — while changing nothing that is running, which is the worst of
  both.) The test gates only *committing* a flip, which should be deliberate.
- *A test pinning a live operational setting is unusual.* It is already the house pattern —
  `test_the_shipped_config_carries_the_floor_the_owner_decided` pins one in exactly this shape,
  and `TODAYS_CRYPTO` pins seven field by field.

It went in `tests/test_config.py`, **not** `test_golden_surfaces.py`: that module is
rendering-equivalence only, every assertion in it compares two rendered strings, and its
docstring makes "asserted whole rather than by sampled substrings" the discipline.

## 8. Job ids in the boot log

`sentinel/core/app.py` collects each id **as it is registered** and adds one field to the
existing `log.info`. It does **not** read `scheduler.get_jobs()` — the `heartbeat` job is
registered first, by the lifespan, and would silently join the list.

```
scheduler.pipeline_scheduled markets=['crypto'] job_ids=['scan:crypto', 'tracker']
  scan_interval_minutes={'crypto': 60} tracker_interval_seconds=60 dry_run={'crypto': False}
```

Verified through the **real** log pipeline, not just `capture_logs` (which bypasses
processors), so the `redact_secrets` suffix list is confirmed not to touch it:

```json
{"markets": ["crypto"], "job_ids": ["scan:crypto", "tracker"], "dry_run": {"crypto": false}, ...}
```

Two tests. One asserts the logged ids equal what the scheduler actually holds — as a **set**
plus a duplicate check, deliberately not as a list, because order is APScheduler's business and
coupling to it would make the test fragile. The other pins the literal strings and their order
once, including the bare `tracker`, because a relationship test cannot see a rename that moves
registration and log together.

On switch-on day the line reads
`job_ids=['scan:crypto', 'scan:forex', 'tracker', 'tracker:forex']`, which is now written into
`docs/DEPLOY.md` §13b step 5.
