## 3. How the goldens are kept honest

Golden files generated by the code they test only prove the code agrees with itself. Each value is checked three ways:

1. **Golden CSVs** — `tests/fixtures/golden/*.csv`, 8 series (BTC/SOL × 15m/1h/4h/1d), compared at **1e-8**, including an assertion that the NaN warm-up masks line up exactly (an off-by-one in the seed would otherwise hide).
2. **Independent reimplementation** — `tests/features/test_indicators.py` contains from-scratch NumPy recurrences for EMA/RSI/ATR, written against the definitions rather than the production code, compared at 1e-8.
3. **Closed forms** — EMA of a constant = that constant; EMA seed = the SMA; RSI of a monotonic rise = 100, of a fall = 0, of a flat tape = 50; ATR of constant-range candles = that range; relative volume of a steady tape = 1.
4. **Third-party oracle** — `pandas-ta` is compared against ours on a 600-bar series (see §4).

Regenerate with `python tests/fixtures/generate_goldens.py` only when an intended change has been justified.

## 4. Decisions made

1. **Indicators implemented directly; `pandas-ta` demoted to a test-only oracle.** ARCHITECTURE §2 lists `pandas-ta`, and it was approved for M2 — but measuring it first showed two problems: it emits **RSI(14) values from bar 1** with no warm-up masking, and its RSI/ATR use an unseeded EWM instead of Wilder's SMA-seeded smoothing. At our 200-bar tails that is a ~1e-5 divergence from the canonical definition, only converging near 400 bars. Since RISK_ENGINE §2 rules 3–4 gate stop distances on ATR multiples, and a value emitted during warm-up would reach the analyst as if it were real, the indicators are implemented here with the conventions written down. `pandas-ta` moved to dev dependencies and now serves as an independent cross-check (`test_pandas_ta_agrees_once_its_seeding_has_decayed`). **This reverses the letter of an approved decision on new evidence — flagging it explicitly for your call.**
2. **Trend regime rules** (owner-approved): five labels, first-match-wins, on the EMA stack plus price. Not defined in any spec, so they live in `regime.py` with a full truth-table test.
3. **Volatility regime**: ATR% ranked against its own trailing 100-bar distribution (<33rd LOW, >67th HIGH) rather than fixed cutoffs, so the same thresholds work for BTC and a small-cap alt.
4. **S/R detection** (owner-reviewed): confirmed fractal pivots, `k=3`, clustered within `0.5 × ATR(14)`, scored `touches × recency_weight` (weight bounded to [0.5, 1.0]), classified against the reference price, top 3 per side, on 1h and 4h. Nothing repaints — the last `k` bars can never be pivots.
5. **Closed candles only.** The in-progress bar is dropped before any indicator runs; `partial_candle_dropped` is recorded per timeframe. `MarketSnapshot.last_price` stays the live price.
6. **`RegimeBasis`** records whether a classification used EMA200 or fell back to EMA20/50 — a reduced read is never presented as a full one.
7. **No Pydantic contract change.** `MarketSnapshot.features` stays `dict[str, Any] | None`; `compute()` returns a typed `SymbolFeatures` and `attach()` stores `model_dump(mode="json")`. Keeps `features → ingestion` one-directional and matches the JSONB column. Round-trips back into the model (tested).

## 5. Deviations from spec

**One, and it was a live bug the demo caught.** DATA_SOURCES §2.1 specifies tails of 200/200/200/100. Because Binance's last candle is still in progress and the engine drops it, those tails yielded only **199 closed candles — so EMA200 could never be computed on any timeframe**, and every regime silently fell back to a reduced basis. `config.yaml` now requests **201/201/201/101**, preserving the spec's lengths as *closed* candles.

The effect was not cosmetic: with EMA200 present, BTC's 4h regime changed from `UPTREND (reduced)` to `RANGE (full)` — the reduced read had been overstating the trend, which would have reached the analyst as context.

## 6. Spec ambiguities resolved

| Ambiguity | Resolution |
|---|---|
| Trend regime rules undefined | Owner-approved 5-label table (§4.2), truth-tested. |
| Volatility regime undefined | Percentile-ranked ATR% (§4.3). |
| S/R algorithm and parameters undefined | Owner-reviewed fractal + ATR clustering (§4.4). |
| Partial candles unmentioned | Dropped before computation (§4.5), flagged per timeframe. |
| EMA200 on the 1d tail | Owner's choice: report `null`, mark the basis `REDUCED`, fabricate nothing. |
| Relative volume baseline undefined | Mean of the **preceding** N bars, current bar excluded, so a spike cannot dilute its own baseline. |

## 7. Notes for M3 (chart renderer)

- `OHLCVSeries.to_frame()` gives mplfinance the float64 frame it wants.
- `SymbolFeatures.levels` carries `price`, `kind`, `timeframe`, `touches` — enough to draw S/R lines with weight.
- Levels are non-repainting, so a chart re-rendered from stored OHLCV is byte-identical — the M3 reproducibility requirement holds by construction.
- Chart EMAs should be drawn from `indicators.ema` rather than recomputed, so the picture and the numbers cannot disagree.
- M3 needs `mplfinance` (>1MB → needs approval).
